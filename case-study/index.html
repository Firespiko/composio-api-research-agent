Researching 100 APIs without researching them by hand.

An automated research pipeline that retrieves developer documentation, extracts structured API intelligence with a local LLM, selectively verifies uncertain results, and turns the evidence into integration-readiness insights.

01 · Problem

The bottleneck is not finding APIs. It's turning inconsistent documentation into comparable data.

Across 100 applications, authentication, credential access, API protocols, SDK availability, MCP support and buildability are documented in very different ways. A manual workflow would require repeatedly searching, reading, interpreting and recording the same classes of information.

05 · Verification

Independent evidence exposed meaningful disagreements.

Verification was performed against a separate search pass. The verifier compared the research record against additional evidence and produced field-level corrections where necessary.

26 / 33

independently verified applications contained at least one actual field-level discrepancy between the original research result and the verification result.

13 API type corrections
13 Access corrections

Verification coverage: 33 / 98

The verification set is not treated as a random sample. These results are therefore used to demonstrate the pipeline's ability to detect discrepancies rather than to estimate the error rate of the entire 100-app dataset.

07 · Patterns

Three patterns emerged from the dataset.

01

REST dominates

REST appeared in 95 of the 98 researched records, making it the dominant API protocol in this dataset.

02

Authentication is rarely uniform

OAuth2, bearer tokens, API keys and API tokens frequently coexist across the application set.

03

Credential access is the less certain layer

39 research records were classified as unknown for credential access, showing why documentation discovery alone is insufficient.

08 · Methodology

Designed as a reproducible research system.

Evidence first

The language model receives retrieved evidence and is instructed to ground structured fields in that evidence rather than relying on unsupported assumptions.

Checkpointing

Research and verification results are persisted incrementally. A failed request does not require restarting the complete 100-app run.

Structured schema

Each application is normalized into authentication, access, API, SDK, MCP, breadth, buildability, blocker and evidence fields.

Independent verification

Verification uses a separate search pass so that the second stage is not simply repeating the first model's evidence interpretation.

09 · Limitations

What the current system does not claim.

01

Confidence is not calibrated probability

The extraction model frequently produced high confidence values. These scores are therefore used for triage, not interpreted as measured probabilities of correctness.

02

Verification is not a random sample

Only 33 applications were independently verified. The observed correction rate should not be extrapolated to all 100 applications.

03

Documentation changes

API documentation, pricing and access requirements can change. Evidence URLs and timestamps are therefore important for production use.

10 · Reproducibility

The case study is generated from the pipeline's outputs.

The repository separates data, retrieval, extraction, verification, analysis and presentation so each stage can be inspected independently.
